## 1. مقدمة

### 1.1 الغرض
هذه الوثيقة تحدد المتطلبات الكاملة لمنصة **Syriacar** — موقع ويب يربط أصحاب المركبات بمزودي خدمات الفحص والسطحة الموثَّقين في صحنايا وريف دمشق. الوثيقة موجَّهة لفريق DB Design وفريق UI/UX وفريق التطوير.

### 1.2 النطاق
- **المنصة:** موقع ويب (PWA) — عربي فقط — Mobile-First.
- **نطاق الإطلاق الأول:** صحنايا، ريف دمشق.
- **الخدمتان:** فحص المركبة + سطحة (نقل مركبة).
- **خارج النطاق:** حجز، دفع، تتبع، تقييمات، AI، تطبيق جوال أصلي.

### 1.3 تعريفات رئيسية

| المصطلح | التعريف |
|---|---|
| مستخدم-ضيف | يستخدم المنصة بدون حساب؛ يُدخل اسمه ورقمه في كل طلب |
| مستخدم-مسجَّل | لديه حساب يحفظ مركباته ومحافظة سكنه |
| مزود | مقدم خدمة فحص أو سطحة، حسابه يُنشئه الفريق |
| طلب خدمة | سجل إنشاء المستخدم لطلب فحص أو سطحة، بغض النظر عن وجود مزود |
| إشعار | سجل توجيه طلب لمزود محدد عند ضغط «أبلغ المزود» |
| مناسب | مزود تنطبق عليه شروط المطابقة لمركبة المستخدم |
| Operations | موظف الفريق يدير المنصة من لوحة الإدارة |
| Super Admin | المدير الأعلى، يدير موظفي Operations |
| OTP | رمز تحقق مؤقت يُرسَل عبر WhatsApp API |
| يوم تقويمي | من 00:00 حتى 23:59 بتوقيت دمشق (UTC+3) — Asia/Damascus |
| E.164 | صيغة الهاتف الدولية القياسية: `+963XXXXXXXXX` |

### 1.4 المراجع
- MVP Syriacar v6.0
- ISO/IEC/IEEE 29148:2018
- whapi.cloud API Documentation
- OWASP Multifactor Authentication Cheat Sheet

## 2. الوصف العام للنظام

### 2.1 ما يفعله النظام
يعرض مزودي خدمات المركبات الموثَّقين للمستخدم، ويُمكِّنه من إرسال إشعار لمزود مختار، ثم يتواصلان هاتفياً خارج المنصة.

### 2.2 ما لا يفعله النظام
لا يحجز، لا يُسعِّر، لا يدفع، لا يتتبع موقع المزود، لا يضمن تنفيذ الخدمة، لا يُرسِل إشعارات آلية لرقم المزود.

### 2.3 مكونات النظام

| المكوّن | الوصف |
|---|---|
| Web App (PWA) | واجهة المستخدم وواجهة المزود — Mobile-First |
| Operations Dashboard | لوحة إدارة الفريق |
| Super Admin Dashboard | لوحة التحكم الأعلى |
| Backend API | منطق الأعمال وقاعدة البيانات |
| WhatsApp API (whapi.cloud) | إرسال OTP فقط |
| OpenStreetMap / Leaflet | عرض الخريطة |

### 2.4 المستخدمون والأدوار

| الدور | الوصف | كيف يدخل |
|---|---|---|
| مستخدم-ضيف | طالب خدمة بدون حساب | مباشرة — لا تسجيل |
| مستخدم-مسجَّل | طالب خدمة بحساب | تسجيل + OTP |
| مزود-فحص | مقدم خدمة فحص | حساب ينشئه الفريق |
| مزود-سطحة | مقدم خدمة نقل | حساب ينشئه الفريق |
| Operations | موظف إدارة | حساب ينشئه Super Admin |
| Super Admin | مدير النظام | **صف bootstrap في `ops_users` بـ`role=super_admin`** |

> **قرار هندسي:** Super Admin ليس حساباً مضمَّناً؛ هو صف عادي يُنشأ أثناء bootstrap النظام.

## 4. متطلبات الواجهات الخارجية

### 4.1 واجهة المستخدم (UI)

- **REQ-UI-001:** الواجهة عربية كاملة (RTL) على كل الشاشات.
- **REQ-UI-002:** Mobile-First؛ تعمل بشكل صحيح على شاشات ≥320px عرضاً.
- **REQ-UI-003:** تدعم الإضافة للشاشة الرئيسية (PWA / Add to Home Screen).
- **REQ-UI-004:** لا تتطلب تثبيت تطبيق من متجر.

### 4.2 الخرائط

- **REQ-MAP-001:** الخريطة الداخلية: OpenStreetMap عبر Leaflet.js.
- **REQ-MAP-002:** روابط الموقع الخارجية (لواتساب): `https://maps.google.com/?q={lat},{lng}`.
- **REQ-MAP-003:** إحداثيات GPS للمستخدم لا تُحفظ على خوادم المنصة أو في logs/history. المحافظة والمنطقة المختارتان يدوياً هما المحلية المستخدمة للمطابقة وتُحفظان لطلب الفحص. لا reverse geocoding أو خدمة geocoding خارجية.

### 4.3 WhatsApp API

- **REQ-WA-001:** المزوِّد: `whapi.cloud`.
- **REQ-WA-002:** الاستخدام الوحيد: إرسال OTP لرقم المستخدم عند التسجيل.
- **REQ-WA-003:** الرقم المُرسِل: رقم مخصص للنظام (ليس رقم الفريق).
- **REQ-WA-004:** Endpoint: `POST https://gate.whapi.cloud/messages/text` مع `Authorization: Bearer {token}` على الخادم فقط، لا token في URL/frontend.
- **REQ-WA-005:** الرقم محفوظ داخلياً E.164. يحوّله adapter إلى digits-only للمزوّد: `{ "to": "963XXXXXXXXX", "body": "رمز التحقق الخاص بك: XXXXXX" }`. body والكود يمران في الذاكرة فقط، ولا يُحفظان في DB أو logs.
- **REQ-WA-006:** محاولة أولى ومحاولة تلقائية واحدة بعد 5 ثوانٍ من الفشل/تعذّر تأكيد الإرسال؛ بحد أقصى محاولتين لكل challenge. بعد الاستنفاد يُعرض فشل الإرسال في O-06b للقراءة فقط. Operations لا يرى الكود ولا يسترجعه ولا يبلّغه شفهياً؛ لا إجراء «تم الاتصال» أو إرسال OTP يدوي.
- **REQ-WA-007:** تُميَّز API acceptance عن التوصيل: HTTP نجاح مع `sent=true` وmessage ID يُسجَّل api_accepted، لا delivered. `sent=false` أو HTTP rejection أو provider status=failed يعني failed؛ timeout دون نتيجة مؤكدة يعني unknown. `pending` أو غياب callback لا يعني الفشل. حالات Whapi تشمل failed/pending/sent/delivered/read/played/deleted؛ delivered/read دليل الوصول، ولا تُفسَّر الحالات الأخرى كفشل افتراضي.
- **REQ-WA-008:** تُحفظ لكل محاولة metadata فقط: attempt_no، attempted_at، api_outcome، http_status إن توفر، provider_sent إن توفر، provider_message_id، provider_status/status_at، وكود/سبب خطأ مُنقَّح. لا body/code/raw payload. تُربط status callbacks بالـmessage ID، تُحمى بـHTTPS وheader سرّي يُهيَّأ في Whapi، وتُعالج idempotently دون أن تغيّر أحداث محاولة قديمة حالة الكود الحالي.

  تُراعى timestamps/تسلسل status المزوّد؛ أحداث متأخرة أو مكررة لا تُرجِع delivered/read إلى pending/sent ولا تُجدِّد retry سبق استنفاده. رد HTTP ناقص أو غير قابل للتفسير دون إثبات acceptance يُسجَّل unknown، لا نجاح افتراضي.
- **REQ-WA-009:** يُحفظ retry_at = failure_time + 5 seconds إن لم تُستنفد المحاولة الثانية ولم ينته challenge. إعادة المعالجة تعتمد العداد والموعد المحفوظين وتمنع محاولة ثالثة. للمحاولة الثانية تُولَّد شفرة جديدة في الذاكرة فقط، يُستبدَل hash وتُبطَل الشفرة القديمة، وتُضبط صلاحية الجديدة لعشر دقائق من المحاولة. لا استرجاع من hash ولا تخزين plaintext، ولا إعادة ضبط عداد محاولات التحقق بسبب retry. بعد الاستنفاد يتبع المستخدم FR-ACC-006.

مرجع العقد المتحقق منه في 2026-10-03: [sendMessageText](https://whapi.readme.io/reference/sendmessagetext)، [تدفق التوصيل](https://support.whapi.cloud/help-desk/getting-started/api-docs)، [OpenAPI](https://panel.whapi.cloud/yaml/openapi.yaml). هذه معلومات إرسال OTP فقط، لا إشعارات WhatsApp آلية للمزود.

### 4.4 واتساب المستخدم (wa.me — ليس API)

- **REQ-WAU-001:** زر «أبلغ المزود» يفتح `wa.me/{providers.whatsapp_number}?text={encoded_message}` في متصفح/تطبيق المستخدم. المصدر: حقل `providers.whatsapp_number` (مستقل عن `phone`).
- **REQ-WAU-002:** المستخدم يضغط «إرسال» بنفسه — لا إرسال آلي من المنصة.
- **REQ-WAU-003:** زر «أرسل موقعي» يفتح `wa.me/{providers.whatsapp_number}?text={encoded_location_message}`.

### 4.5 Browser Push Notification

- **REQ-BPN-001:** عند وصول إشعار جديد لمزود، تُرسَل push notification للمتصفح إن دعمها.
- **REQ-BPN-002:** النظام لا يُلزم المزود بقبول الإشعارات — ميزة اختيارية.
- **REQ-BPN-003:** عدم دعم الإشعارات لا يؤثر على أي وظيفة أساسية.
- **REQ-BPN-004:** اشتراكات Push تُخزَّن في `provider_push_subscriptions`؛ مزود واحد قد يملك عدة اشتراكات (أجهزة متعددة).

- **REQ-BPN-005:** VAPID keys تُخزَّن كـenvironment variables (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`). لا تُخزَّن في DB.

## 5. المتطلبات الوظيفية

> **اصطلاح الترميز:** FR = Functional Requirement؛ الأرقام تسلسلية داخل كل قسم.

---

### 5.1 إدارة حساب المستخدم

#### 5.1.1 التسجيل

- **FR-ACC-001:** يُتيح النظام للمستخدم التسجيل بإدخال: الاسم + رقم هاتف سوري + كلمة مرور. الرقم يُخزَّن بصيغة E.164 (`+963...`) بعد التطبيع.
- **FR-ACC-002:** بعد إرسال النموذج يُنشأ المستخدم بـis_active=false ويُرسَل OTP عبر WhatsApp API. challenge غير مستهلك وغير منتهٍ؛ صلاحية التحقق منفصلة عن حالة الإرسال.
- **FR-ACC-003:** OTP صالح لمدة **10 دقائق** من وقت الإرسال (`expires_at`). كود OTP يُخزَّن مُشفَّراً (hash) لا plaintext.
- **FR-ACC-004:** المستخدم يُدخل OTP في الواجهة للتحقق وتفعيل حسابه.
- **FR-ACC-005:** الحساب يُفعَّل فور التحقق الصحيح من OTP — لا انتظار. سجل OTP يُحدَّث بـ`consumed_at`.
- **FR-ACC-006:** بعد الانتهاء أو الإبطال باستنفاد محاولات التحقق، تُتاح إعادة الإرسال بشرط مرور دقيقتين على آخر محاولة إرسال. تُنشأ challenge جديدة ويُبطَل القديم، مع hash جديد ومحاولتي إرسال كحد أقصى حسب REQ-WA-006–009. لا إعادة إرسال بواسطة Operations.
- **FR-ACC-007:** أرقام الهاتف المقبولة: `+963` فقط (سورية). النظام يرفض أي رقم لا يبدأ بـ`+963`.
- **FR-ACC-007b:** الحد الأقصى لمحاولات إدخال OTP: 5 محاولات. عند تجاوزه يُلغى السجل الحالي ويُطلب إعادة إرسال.

#### 5.1.2 تسجيل الدخول والجلسة

- **FR-ACC-008:** يُتيح النظام تسجيل الدخول برقم الهاتف (E.164) + كلمة المرور.
- **FR-ACC-009:** مدة الجلسة: **30 يوماً** من آخر نشاط — ثم يُطلَب إعادة الدخول.
- **FR-ACC-010:** الجلسة تُخزَّن في cookie/token آمن (HttpOnly).
آلية التخزين: **JWT** مُوقَّع (HS256) في `HttpOnly Secure cookie`.لا `sessions table` في DB. لا متطلب invalidation فوري في MVP.

#### 5.1.3 حذف الحساب

- **FR-ACC-011:** المستخدم المسجَّل يستطيع حذف حسابه من إعدادات ملفه الشخصي.
- **FR-ACC-012:** عند الحذف transactionally: is_deleted=true وis_active=false، ثم name/phone → NULL. تسمح DB بـNULL للمحذوف، وتتطلبهما لغير المحذوف. سجلات الإشعارات والطلبات تبقى للإحصاء مع user_id للربط فقط.
- **FR-ACC-012b:** مركبات المستخدم المحذوف: brand_group_id وbrand_id وyear وfuel_type وvehicle_category تبقى؛ plate_number وcolor وnotes → NULL.
- **FR-ACC-013:** الحذف نهائي — لا استرداد.

#### 5.1.4 حفظ محافظة السكن

- **FR-ACC-014:** المستخدم المسجَّل يستطيع حفظ محافظة سكنه (اختياري).
- **FR-ACC-015:** محافظة السكن تُستخدَم كقيمة افتراضية لمحافظة الانطلاق في طلب السطحة.

#### 5.1.5 الاستخدام كضيف

- **FR-ACC-016:** يُتيح النظام استخدام خدمة الفحص والسطحة بالكامل بدون حساب.
- **FR-ACC-017:** الضيف يُدخل اسمه وهاتفه قبل إنشاء كل طلب: اختيار مزود → بيانات الضيف → التأكيد → الطلب والإشعار. notifications الإضافية للطلب نفسه تعيد استخدام بياناته. تُحفظ guest_name/guest_phone سنة ثم حذف؛ تُرسَل للمزود عند إنشاء notification فقط. مسار الفحص no_match محدد في FR-INS-015.

### 5.2 إدارة المركبات (للمسجَّل)

#### 5.2.1 إضافة مركبة

- **FR-VEH-001:** المستخدم المسجَّل يضيف مركبة بالحقول التالية:

| الحقل | النوع | إلزامية؟ | القيم |
|---|---|---|---|
| مجموعة الماركة | قائمة | ✅ | ياباني / كوري / أوروبي / أمريكي / صيني / أخرى |

- **FR-VEH-001b:** الماركة المُختارة يجب أن تنتمي للمجموعة المُختارة — يُطبَّق على مستوى التطبيق.
- **FR-VEH-002:** رقم الشاسيه (VIN) لا يُجمَع ولا يظهر في النموذج.
- **FR-VEH-003:** فوق حقل سنة الصنع يظهر توضيح: «(1970–1999) كلاسيكية · (2000–2011) متوسطة · (2012–الآن) حديثة».
- **FR-VEH-004:** لا حد أقصى لعدد المركبات المحفوظة.
- **FR-VEH-005:** المركبة تُفعَّل فوراً بعد الإضافة وتدخل المطابقة — حالة «قيد التوثيق» داخلية للفريق فقط.

#### 5.2.2 التحقق من المركبة (عملية داخلية)

- **FR-VEH-006:** الفريق يراجع أسبوعياً بيانات المركبات مع وزارة النقل يدوياً (رقم اللوحة + الماركة + السنة).
- **FR-VEH-007:** حالة المركبة في DB: `pending_verification` (افتراضي) | `verified` | `rejected`.
- **FR-VEH-008:** حالة `pending_verification` لا تُعرَض للمستخدم ولا تحجب أي ميزة.
- **FR-VEH-009:** إن رُفضت المركبة (Operations يُغيِّر الحالة إلى `rejected`): تُحظر إمكانية استخدامها في طلبات الخدمة الجديدة؛ يتواصل الفريق مع المستخدم خارج المنصة؛ لا يُحظر الحساب.
- **FR-VEH-010:** المستخدم يستطيع تعديل بيانات مركبة مرفوضة وإعادة إرسالها (تعود للحالة `pending_verification`).

### 5.3 طلب الفحص

#### 5.3.1 عرض المزودين (الخريطة)

- **FR-INS-001:** اختيار المحافظة والمنطقة يدوياً إلزامي للفحص ولو نجح GPS؛ لا reverse geocoding. GPS اختياري للعرض فقط ولا يحدد المطابقة.
- **FR-INS-002:** تُعرض خريطة OpenStreetMap لمزودي الفحص active/open في المحافظة والمنطقة المختارتين؛ GPS إن توفر يمكن أن يدعم العرض دون تغيير المحلية.
- **FR-INS-003:** اختيار المحافظة/المنطقة متاح دائماً كمسار أساسي؛ تعذّر GPS لا يمنع البحث.
- **FR-INS-004:** إن كان الإنترنت ضعيفاً (timeout > 5 ثوانٍ): تُعرَض قائمة نصية بالمزودين المفتوحين.
- **FR-INS-005:** المزودون المغلقون لا يظهرون في أي عرض.

#### 5.3.2 المطابقة للمسجَّل

- **FR-INS-006:** المستخدم المسجَّل يختار مركبة من مركباته المحفوظة.
- **FR-INS-007:** يُميَّز المزودون «المناسبون» بدبوس بلون مختلف.
- **FR-INS-008:** الضيف يرى جميع المزودين المفتوحين بلون واحد.

#### 5.3.3 بطاقة المزود

- **FR-INS-009:** عند الضغط على دبوس المزود تظهر بطاقة تتضمن: اسم المزود التجاري، المنطقة، مجموعات الماركات، الماركات المحددة، فئات السنوات، أنظمة الطاقة، فئة المركبة، التخصصات (للعرض فقط)، ساعات العمل، زر «أبلغ المزود».

#### 5.3.4 طلب الخدمة والإشعار

- **FR-INS-010:** عند أول تأكيد «أبلغ المزود» يُنشأ service_request بمحلية الفحص وnotification في transaction. اختيار/تأكيد مزودين إضافيين لنفس الطلب يضيف notifications بالـservice_request_id نفسه. يُفتَح wa.me/{providers.whatsapp_number} ويظهر phone؛ لا إنشاء طلب من مجرد render.
- **FR-INS-011:** قبل الإرسال يظهر تنبيه الموافقة على شروط الاستخدام.
- **FR-INS-012:** للضيف يظهر إضافياً: «سيُرسَل رقمك للمزود لكي يتواصل معك.»
- **FR-INS-013:** قالب رسالة الفحص (مسجَّل): «أنا مستخدمك من «Syriacar»، اسمي [الاسم]، وأريد فحصاً لسيارة [الماركة - السنة].»
- **FR-INS-014:** قالب رسالة الفحص (ضيف): «أنا مستخدمك من «Syriacar»، اسمي [الاسم]، رقمي [الرقم]، وأريد فحصاً لسيارتي.»

#### 5.3.5 حالة «لا يوجد مزود مطابق»

- **FR-INS-015:** عند عدم وجود مزود مفتوح في المحلية أو مناسب للمركبة: «لا يوجد مزود مطابق في نطاقك — يمكنك التواصل معنا على [system_config.contact_phone].» للضيف: فحص → المحافظة/المنطقة → الاسم/الهاتف → التأكيد → service_request بـno_match والمحلية المحفوظة، بلا اختيار مزود وبلا notification. للمسجَّل تُستخدم هويته ومركبته المختارة مع تأكيد الطلب. لا search expansion ولا إنشاء طلب من render/refresh. الرقم من system_config، لا hardcode.

### 5.4 طلب السطحة

#### 5.4.1 اختيار المحافظات

- **FR-TOW-001:** تظهر حقلا «محافظة الانطلاق» و«محافظة الوصول».

#### 5.4.2 عرض مزودي السطحة

- **FR-TOW-005:** القسم الأول «مناسب لمشكلتك»: مزودو towing active/open يغطون كلتا المحافظتين + تنبيه ثابت. القسم الثاني «باقي المزودين»: مزودو towing active/open لا يغطون كلتيهما. لا مغلقين أو غير active في القسمين.
  **قاعدة الترتيب داخل القسم الأول:** مزود مقره (`governorate_id`) = محافظة الانطلاق أولاً ← مزود مقره = محافظة الوصول ثانياً ← الباقون بترتيب عشوائي (`ORDER BY RANDOM()`). إن غاب طرف تُطبَّق القاعدة جزئياً؛ إن غابا معاً → عشوائي بالكامل.
- **FR-TOW-006:** إن غاب مزودون يغطون المحافظتين معاً: القسم الأول فارغ وتبقى قائمة الباقين. تظهر في القسم الأول الفارغ رسالة: «لا يوجد مزود يغطي هذا المسار — يمكنك التواصل معنا على [system_config.contact_phone].»

#### 5.4.3 بطاقة مزود السطحة

- **FR-TOW-007:** البطاقة تتضمن: الاسم التجاري، المحافظات التي يغطيها، نوع السطحة، رقم الهاتف، زر «أبلغ المزود».

#### 5.4.4 طلب الخدمة والإشعار وإرسال الموقع

- **FR-TOW-008:** أول تأكيد يُنشئ service_request وnotification transactionally؛ التأكيدات التالية تضيف notifications للطلب نفسه. notification واحدة على الأقل لمزود Section A وقت إنشائها تعني matching_status=matched؛ إن كانت كلها Section B فـno_match. يُحدَّث status للطلب transactionally، ولا يُنزَل matched بسبب إضافة Section B لاحق. لا status لكل notification؛ رابط wa.me يستخدم whatsapp_number.
- **FR-TOW-009:** قالب رسالة السطحة (مسجَّل): «أنا مستخدمك من «Syriacar»، اسمي [الاسم]، وأريد سطحة.»
- **FR-TOW-010:** قالب رسالة السطحة (ضيف): «أنا مستخدمك من «Syriacar»، اسمي [الاسم]، رقمي [الرقم]، وأريد سطحة.»
- **FR-TOW-011:** بعد الإشعار تظهر رسالة «أرسل موقعك للمزود» مع زر يفتح واتساب.
- **FR-TOW-012:** قالب towing_location: «Syriacar — [الاسم] — سطحة — موقعي: [الموقع]». [الموقع] = `https://maps.google.com/?q={lat},{lng}` عند توفر الإحداثيات، وإلا «محافظة [اسم المحافظة]، منطقة [اسم المنطقة]».
- **FR-TOW-013:** المحافظة والمنطقة اليدويتان مسار صريح عند غياب/رفض GPS؛ لا يُفترض عمله في سوريا. هذه محلية مشاركة الموقع وليست تغييراً لمحافظتي مسار الطلب. لا GPS history أو geocoding أو خدمة موقع جديدة.

#### 5.4.5 التنبيه الثابت

- **FR-TOW-014:** تنبيه ثابت في كل خطوات السطحة: «التواصل يعتمد على استجابة المزود، والإشعار ليس حجزًا ولا ضمانًا.»

### 5.9 منطق المطابقة

#### 5.9.1 المطابقة للفحص

مزود فحص مناسب = active + is_open + governorate_id/region_id يساويان المحلية المختارة + يدعم brand_group وbrand وyear_category وfuel_type وvehicle_category للمركبة المختارة. الضيف يرى active/open في المحلية دون مطابقة مركبة؛ لا GPS-radius أو distance matching.

#### 5.9.2 المطابقة للسطحة

مزود مناسب = active + is_open + provider_coverage يشمل كلتا المحافظتين.

matching_status للطلب هو OR عبر نتائج Section A وقت إنشاء notifications: واحدة مناسبة تكفي لـmatched، وكلها Section B تعني no_match. يُحفظ القرار على الطلب لا notifications؛ لا يُعاد تصنيف التاريخ عند تغيير بيانات المزود.

#### 5.9.3 حساب is_open

```
is_open = (
  work_days[weekday(Asia/Damascus)].enabled = true
  AND Damascus_CURRENT_TIME ∈ [work_days[weekday].start, work_days[weekday].end]
  AND NOT (today_closed = true AND today_closed_date = Damascus_TODAY)
)
```

## 6. المتطلبات غير الوظيفية

### 6.1 الأداء
- **NFR-PERF-001:** استجابة API الأساسية ≤ 2 ثانية في الأحوال الاعتيادية.
- **NFR-PERF-002:** First Contentful Paint ≤ 3 ثوانٍ على شبكة 3G.
- **NFR-PERF-003:** عرض القائمة النصية البديلة ≤ 1 ثانية بعد timeout الخريطة.

### 6.2 الأمان
- **NFR-SEC-001:** كلمات المرور مُشفَّرة (hash) — لا تُخزَّن plaintext.
- **NFR-SEC-002:** OTP يُخزَّن hash فقط — لا plaintext.
- **NFR-SEC-003:** الجلسات تُخزَّن في HttpOnly cookies.
- **NFR-SEC-004:** HTTPS إلزامي على كل الاتصالات.
- **NFR-SEC-005:** whapi token لا يظهر في Frontend.
- **NFR-SEC-006:** الـIDs الداخلية لا تُعرَض للمستخدم النهائي.
- **NFR-SEC-007:** Rate limiting على OTP وعمليات التسجيل.
- **NFR-SEC-008:** RBAC ثابت في الكود — deny-by-default.

### 6.3 قابلية الاستخدام
- **NFR-USE-001:** RTL كامل.
- **NFR-USE-002:** Touch targets ≥ 44×44px.
- **NFR-USE-003:** خط ≥ 14px.
- **NFR-USE-004:** Fallback لكل ميزة تعتمد GPS أو الخريطة.

### 6.4 التوفر
- **NFR-AVA-001:** المنصة تعمل مع تقطع الاتصال — App Shell يُعرَض.

### 6.5 الصيانة
- **NFR-MAI-001:** الكود قابل للتوسع لمناطق جغرافية جديدة دون تعديل جوهري.

### 6.6 الاحتفاظ بالبيانات
- **NFR-DAT-001:** service_requests وnotifications: سنة واحدة ثم حذف أو تجميع.
- **NFR-DAT-002:** otp_verification_challenges: حذف بعد consumed أو expired.
- **NFR-DAT-003:** provider_push_subscriptions: حذف عند is_active=false أو expires_at.
- **NFR-DAT-004:** audit_log: **12 شهراً** — قرار مؤقت؛ مراجعة قبل الإنتاج.
- **NFR-DAT-005:** تنفيذ cleanup لـ`service_requests`/`notifications`/
`audit_log` يُؤجَّل لما قبل الشهر الثاني عشر من الإنتاج.
تُراجَع الآلية (GitHub Actions cron + protected endpoint)
قبل بلوغ أي سجل عمر سنة.

### ب-2 قواعد النزاهة المنطقية

- `user_type='registered'` ↔ `user_id NOT NULL`, `guest_name/phone NULL`
- `user_type='guest'` ↔ `user_id NULL`, `guest_name/phone NOT NULL`
- inspection → inspection_governorate_id/inspection_region_id NOT NULL وorigin/dest NULL؛ vehicle_id مطلوب للمسجَّل فقط
- `service_type='towing'` ↔ `origin_governorate_id NOT NULL`, `dest_governorate_id NOT NULL`
- towing → inspection_governorate_id/inspection_region_id NULL
- inspection_region_id ينتمي لمحافظة الفحص؛ تحقق التطبيق قبل الحفظ/المطابقة
- is_deleted=false → name/phone NOT NULL؛ is_deleted=true → name/phone NULL وis_active=false
- **`providers.service_type='towing'` ↔ capability junctions (brands/year_categories/fuel_types/vehicle_categories) لا تُملأ؛ UIUX يُخفي الحقول في O-02**
- `today_closed=false` ↔ `today_closed_date IS NULL`
- `today_closed=true` ↔ `today_closed_date IS NOT NULL`
- `providers.whatsapp_number` ↔ E.164؛ UNIQUE؛ NOT NULL؛ مستقل عن `phone`

تُطبَّق على مستوى التطبيق. CHECK بالجدول للقواعد أحادية الصف حيثما دعم الـDBMS.
