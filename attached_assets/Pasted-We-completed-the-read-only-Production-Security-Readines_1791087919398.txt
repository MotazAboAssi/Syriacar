BLOCKER 1 — Registration takeover / incomplete-account replacement
Current issue:
An unactivated account can be re-registered by phone, replacing its name/password hash and creating a new OTP challenge. OTP verification is tied to the latest phone challenge, not strongly to the specific registration attempt and credentials.

Goal:
Ensure an attacker who knows a phone number cannot replace the pending registration credentials and have the legitimate user accidentally activate the attacker's chosen password.

Design requirements:
- Preserve the existing legitimate registration/OTP UX as much as possible.
- Do not expose whether a phone belongs to a registered or pending account beyond the existing intended messages.
- OTP must remain hash-only.
- Do not weaken OTP attempt limits/cooldown.
- Do not add unnecessary schema unless genuinely required.
- Prefer the smallest secure design.
- Explain exactly how an existing pending registration is handled.
- Explain what happens when the legitimate user starts registration again.
- Explain how verification proves that the OTP belongs to the registration attempt being activated.

BLOCKER 2 — Persistent/shared rate limiting
Current issue:
Rate limits are stored in an in-memory Map in one Node process, so restarts and multiple instances bypass them. Login limits are also based on phone+IP.

Goal:
Provide effective shared rate limiting suitable for the actual Replit production deployment.

Constraints:
- Do not invent infrastructure that Replit does not provide.
- Inspect the existing project/deployment architecture first.
- Prefer an existing PostgreSQL-backed mechanism if appropriate, but do not create a complex generic rate-limit framework unnecessarily.
- Preserve legitimate users behind NAT/shared IPs.
- Include both account/phone-oriented and IP-oriented protection where appropriate.
- Include registration, login, OTP send/resend, and other security-sensitive endpoints.
- Include Guest request abuse protection where appropriate, but keep that as a separate concern from authentication limits.
- Explain cleanup/retention of rate-limit records if database-backed.
- Avoid unbounded database growth.
- Keep the implementation MVP-sized.

BLOCKER 3 — Guest request abuse
Current issue:
Guest inspection/towing request creation has no application-level rate limiting/quota.

Goal:
Prevent automated abuse and database exhaustion while preserving the approved Guest UX.

Constraints:
